# 02.02 - Why structure matters

**Why this step matters:** Compare route-first chaos with a small feature-oriented structure.

## The common trap

The obvious approach is to keep everything close to the page where you first need it: data in components, validation in event handlers, one-off styles beside every section, and route handlers that each invent their own rules. It feels fast for a day and expensive for the rest of the project.

The cost shows up as duplicated logic, inconsistent error messages, unsafe public/private boundaries, and pages that are difficult to change without breaking another route.

## The professional approach for this portfolio

Keep responsibilities narrow:

| Concern | Belongs in |
|---|---|
| Routes and metadata | `app/` |
| Reusable UI | `components/` |
| Data access and helpers | `lib/` |
| Database schema and migrations | `prisma/` |
| Static project media | `public/projects/` |
| Project policies | `docs/` |

This is not abstraction for its own sake. It lets the public portfolio, the article system, and the admin workflow share behavior without sharing secrets or UI assumptions.

## Contract to carry forward

```text
Public pages can read published content.
Admin pages require a valid admin session.
API mutations validate input on the server.
Secrets live in environment variables, never in client code.
```
